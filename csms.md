# Charging Station Management Systems (CSMS)

A CSMS is the backend a charging station talks to over OCPP. This file lists the
ones we can document from verifiable sources, in a single table, so the two
questions that usually matter — *is it certified?* and *is it open source?* —
are columns rather than separate lists. They cross more often than expected:
CitrineOS is both, while SteVe is open source but not certified — its
maintainers ship a separately certified commercial build under another name.

This is a companion to the [main list](README.md), which covers tools and
libraries rather than products.

## How to read this list

### Where each column comes from

| Column | Source |
| --- | --- |
| Product, Company, HQ, OCPP, Certificates | [OCA certified products registry](https://openchargealliance.org/certified-companies/), mirrored into `csms-certificates.csv` — except Certificates, any of these may be completed or overridden by a curated row, which is how non-certified products get them at all |
| OCA-certified | Derived — `Y` if the product appears in the OCA registry |
| Open-source | Derived — `Y` if the row declares `open_source`, or names a repository we could reach |
| Features | Derived from the certificate type (see below) for certified products; curated and sourced otherwise |
| First release, Latest version | GitHub API for open-source entries; curated and sourced otherwise. **Latest version links to the product's changelog** when one is published — for open-source entries that is the GitHub releases page |
| API, Pricing, Website, Founded, OCPI, Status | Curated in `csms.csv`, each value backed by a URL in its `sources` column |

An empty cell means *not known from a source we can cite*, never *no*. Curated
cells without a source are not accepted — see
[Contributing to this list](#contributing-to-this-list). A handful of values
carry `contributor:<name>` instead of a URL in `csms.csv`: a maintainer
asserted them from their own research and nobody has found a public citation
yet. The row's `notes` says so, and such a value is a candidate for upgrading,
not a verified fact.

**Company** links to the vendor's **OCA participant page** — not its own site —
where the registry provides one (158 of the 293 certificates). That page lists
the vendor's certificates and postal address. The vendor's own site, when
known, is in the `Website` column.

**API** is `Y` — linked to the specification — only when the vendor publishes
API documentation reachable without an account. Several platforms document
their API behind a customer login; those read as empty here, which means
*unverified*, not *no API*.

**Pricing** distinguishes three cases, each linked to the page it came from:
`Price list` (figures published), `On request` (a pricing page exists but quotes
nothing), `Published` (a pricing page exists, contents not verified).
`Free (self-hosted)` marks open-source projects — it describes the software,
not any hosted offering the same vendor may sell.

Columns kept in `csms.csv` but not rendered here, to keep the table readable:
ISO 15118 support, Eichrecht, licence, deployment model, HQ city, notes and
sources.

### What gets a row

Every OCA-certified CSMS, plus any company publishing a **named, OCPP-based
charging-station management platform** — software-only or sold alongside its
own hardware. Deliberately excluded: charge point operators that merely run a
network without selling the platform (Pod Point, ChargeZone, Statiq, Izivia,
Freshmile…), roaming hubs (Hubject, Gireve), and hardware vendors whose portal
has no distinct product name. These omissions are a scope choice, not an
oversight.

The line that catches most candidates out is the one between a CSMS and the
layers that sit next to it. A product that optimises energy, shaves peaks,
schedules sessions or resells a driver app on top of *someone else's* CSMS is
not one. FLEXECHARGE draws that line itself: "HARMON-E is not a CPMS
replacement. It works alongside CPMS platforms" — its gateway is "a standard
OCPP proxy, which relays incoming messages from connected charging stations to
any freely selectable Charge Point Management System". Peak Energy is just as
blunt: "Peak Energy is not another CPMS or energy platform. It is a specialized
DSO pricing and capacity insights service that sits alongside your existing
systems." Scopt Powerconnect (a smart-charging overlay working "with any
CPMS"), Perific (home energy metering that reports *into* Monta and AMPECO),
Vourity (unattended-payment terminals) and Fell Tech (home automation treating
a charger as one schedulable load) are out on the same test, despite appearing
on charger vendors' integration-partner pages next to real CSMS.

The test cuts both ways. Invisia markets itself as building energy management,
but its service list includes hardware-less OCPP station management, RFID card
issuance, tariffs and roaming — so it is in. What a vendor calls itself matters
less than whether it terminates OCPP and manages the stations.

Beware name collisions when checking a vendor against the registry: the
OCA-certified `ELOCITYTECH INC` (Canada, "HIEV CSMS") is unrelated to the
Polish `elo.city`, and the certified `Everon CO., Ltd.` (Republic of Korea) is
unrelated to the Dutch Everon platform.

### How features are derived

The OCA publishes a certificate *type* rather than a feature list. The
single-letter codes are expanded using the legend from the registry's own
`Certificate type` filter:

| Code | Feature |
| --- | --- |
| `S` | Advanced Security |
| `L` | Local Authorization List Management |
| `C` | Smart Charging |
| `D` | Advanced Device Management |
| `R` | Reservation |
| `U` | Advanced User Interface |
| `I` | ISO 15118 Support |

`Core` and `Security` map to themselves. `Subset` and `Family` are scope
qualifiers, not feature sets, and contribute nothing.

`Full` is the one expansion the OCA legend does not spell out. On OCPP 1.6 we
read it as the six feature profiles the OCPP 1.6 specification defines — Core,
Firmware Management, Local Authorization List Management, Reservation, Smart
Charging and Remote Trigger. **This expansion is our inference, not an OCA
statement.** The raw certificate type is kept in the `Certificates` column so
the derivation can be checked against the certificate PDF.

On OCPP 2.0.1, `Full` is deliberately **not** expanded. No CSMS certificate uses
it today, and guessing "Core plus every block" would publish an inference that
reads exactly like a derived feature. It is treated as an unknown token instead,
which fails the render — so the first such certificate forces a decision rather
than a guess.

A product holding several certificates gets the union of their features; 19
products are certified on both OCPP 1.6 and 2.0.1.

### One row per product, not per certificate

The registry issues a certificate per product *and software version*, and
vendors often bake that version into the product name — `eBAB Server v1.6` and
`eBAB Server v1.6.1` are one product, certified twice. A trailing dotted
version is therefore stripped before grouping. A few vendors go further and
rename the platform between certificates; those are merged through a small
hand-maintained alias table in `csms.py` (Driivz, NEC, KEPCO KDN, Elvo,
I-Charge Solutions). Nine such duplicates are collapsed today.

Merging never hides evidence: the **Certificates** column lists *every*
certificate the product holds, each with its OCPP version, certificate type,
the certified software version in parentheses, and a link to the PDF.
`csms-certificates.csv` remains the unmerged, one-row-per-certificate record,
including registration dates.

Two products from one vendor are only merged when the certificates clearly
describe the same platform. Vendors legitimately ship several CSMS products,
and the registry also contains a few entries that look like hardware model
numbers filed under the CSMS product type — those are left alone.

### Three caveats worth reading before drawing conclusions

**A missing feature is not an absent feature.** Certification is opt-in and
costs money. A vendor certified for `Core` alone may well support Smart
Charging without having certified it. The `Features` column is evidence of
what was certified, not an inventory of what the product does.

**Certification applies to a product and a software version, not to a brand.**
The `Certificates` column links each certificate PDF, which names the exact
software version tested. A vendor being in this list says nothing about the
version you are about to deploy.

**The certified set is geographically skewed.** 194 of the 293 CSMS
certificates are held by South Korean companies, because certification is
effectively required there. The OCA registry is an exhaustive list of
*certified* CSMS, not a representative sample of the market — several major
platforms are absent simply because they never applied.

## Contributing to this list

The table between the markers above is generated by `python csms.py render` —
do not edit it by hand.

- **OCA data** lives in `csms-certificates.csv`, a mirror refreshed by
  `python csms.py fetch`. Never edit it; corrections belong upstream with the
  Open Charge Alliance.
- **Everything else** lives in `csms.csv`, which no script ever writes. Add a
  row there to introduce a non-certified product, or to attach facts the
  registry does not carry.

To attach curated facts to an already-certified product, fill `oca_company` and
`oca_product` with the exact strings from `csms-certificates.csv`; the render
merges the two rows. A mismatch prints a warning rather than failing, since the
OCA does rename and withdraw entries.

Every curated value needs a URL in that row's `sources` column. If you cannot
cite it, leave the cell empty.
